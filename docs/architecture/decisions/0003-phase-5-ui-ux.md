# ADR 0003: Phase 5 UI/UX (Midnight), theme preference and delete

Status: implemented on `feature/phase-5-ui-ux`; merge into `main` awaits owner approval and acceptance (`docs/coordination/status-register.md`).

## Context
Phase 5 restyles the application to the approved Midnight direction (dark navy workspace with a matching Light theme, three panes, status told in words first and colour second) and adds a small set of functional features the design needs. The Phase 3 (accounts, import, synchronization, conflicts) and Phase 4 (device-local reminders, tray, notifications) behaviour is accepted and must not change. Pull requests #15 and #16 were written on branches without Phase 4 and are reference implementations only: no code was merged or cherry-picked wholesale; the settings store, theme controller, theme scope and bundled fonts were reused after review against `main`.

## Decisions
1. **Presentation and function are kept apart.** Everything in the design that restyles something that already works on `main` changes no behaviour. Seven functional additions carry their own tests: Light/Dark/System theme, the Dashboard view, the status filter, quick add, delete task and delete project, the severity presentation of sync state, and the inline reminder editor. A sign-out gate (below) is the one behaviour the design implied that `main` did not have.
2. **Theme preference is per device, not per account.** It is stored in `settings.json` beside the local database (`FileSettingsStore`, written through a temporary file and a rename). It is never in the task database, never in the outbox, never synchronized, and it survives an account switch. A damaged file falls back to System. A theme change never touches selection, draft or the unsaved-change gate (`ThemeController` is separate from the workspace). The 21 colour tokens are the authoritative `tokens.json` values; `severity-warning`, `severity-critical` and `on-severity` are new and alias `status-review`, `status-overdue` and `on-accent`.
3. **One navigation target is added:** `DashboardSelection` in `NavSelection`. It has no task rows (`inSelection` is false), entering it goes through the same gate as any navigation, and persisted state is unaffected (selection is not persisted).
4. **Status filter is like sort:** never gated, never touches the draft. A selected task the filter hides stays selected and the existing "hidden in this view" notice shows. Creating a task the filter would hide clears the filter. Chip counts are the scoped tasks (selection and search) per status.
5. **Quick add** creates a root task through `requestCreateRootTask`, the path the New task dialog uses, so validation, the gate and the outbox rules all apply. Enter is guarded in the keymap so the list shortcuts never take it from the field.
6. **Delete** uses the repository's existing single-transaction tree delete (`softDeleteTaskTree`, `softDeleteProjectTree`), exposed to the workspace through an optional `TreeDeleter` capability like `ProjectStore`. Rules: soft delete (tombstones); for a synchronized subtree one delete operation lists the whole subtree, applied by the server completely or not at all (S3); refused while a change runs or the gate is open; the last project cannot be deleted; a failure changes nothing; a project with unsaved edits inside is not deleted silently; there is no keyboard shortcut. Reminders of a deleted task and its subtasks are cancelled. The subtree-delete review item is closed as verified against `main` (data layer, S3, two-device E2E and HTTP tests); this phase adds the application-level flow, the controls and regression tests (`test/features/tasks/data/workspace_delete_sqlite_test.dart`, `test/features/tasks/application/task_workspace_phase5_test.dart`).
7. **Sign-out goes through the gate.** Signing out replaces the workspace, so an unsaved draft would be lost. `requestSignOut` follows the pattern of `requestExit`: at once when clean, otherwise the gate opens and Save or Discard releases it (`signOutReady`).
8. **Sync severity is one pure function** (`describeSync`, `lib/app/sync_presentation.dart`) with the precedence of `SyncStatusBar.describe` (phase, conflicts, refused, pending). The sidebar card shows every state; only the four critical states (conflicts, sign-in needed, device removed, sync stopped) take the alert bar, which cannot be dismissed. With `NEXORA_SYNC` off only "Local only" is reachable and no bar can appear. The old `SyncStatusBar` and `AccountBar` widgets stay in the code for their tests and `describe`; the shell no longer uses them.
9. **Shell:** sidebar 248 and details 380 wide (were 240 and 360); the three stacked bars leave the shell; breakpoints (1100, 900) and their three behaviours are unchanged.
10. **Fonts:** Manrope and Space Grotesk are bundled as variable fonts (SIL OFL) declared once per weight used. No package dependency is added.

## Consequences
- No schema change, no new synchronized field, no change to outbox, pull or conflict contracts, no hosted change.
- Existing tests keep their assertions except where the approved design forces a change; each is listed in `docs/operations/phase-5-implementation-record-2026-11-16.md`.
- A real-window acceptance on Windows (both themes, scaling, sizes) is required before merge (`docs/operations/phase-5-acceptance.md`).
